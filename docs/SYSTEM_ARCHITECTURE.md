# System Architecture

## 1. Overview

A **modular monolith** on Next.js. One codebase, one deployment, one PostgreSQL database, strict internal module boundaries.

```
                ┌──────────────────────────── Next.js 16 app ─────────────────────────────┐
 Visitors ───▶  │ (public) pages ──▶ cms.public queries (published only)                  │
                │       └─ Chatbot widget ──▶ /api/v1/chat ──▶ src/chatbot (RAG) ──┐      │
 Staff/Parents  │ erp/* pages + server actions ─┐                                    │      │
 /Students ──▶  │ /api/v1/* route handlers ─────┼──▶ modules/*.service ──▶ Prisma ──┼──▶ PostgreSQL (+pgvector)
                │ /api/webhooks/payments ───────┘     │  authorize()  audit()        │      │
                │                                      ├─▶ StorageAdapter ──▶ disk / S3     │
                │                                      ├─▶ PDF renderer                     │
                │                                      └─▶ NotificationDispatcher (in-app; email/SMS later)
                └──────────────────────────────────────────────────────────────────────────┘
```

## 2. Key decisions (ADR log)

| # | Decision | Rationale | Alternatives rejected |
|---|---|---|---|
| ADR-001 | Modular monolith in Next.js (no separate backend) | One team, one school; shared Zod types end-to-end; simpler deploy. Module boundaries keep a later split possible. | Separate NestJS API (more infra, duplicated types) |
| ADR-002 | **Single-tenant** (one school per deployment) — confirmed and detailed by ADR-030 | Spec targets one real school. Removes `schoolId` from every query and a whole class of data-leak bugs. | Multi-tenant SaaS (can be added later via `tenantId` + RLS) |
| ADR-003 | Custom DB sessions, not JWT | Instant revocation (deactivate user, logout everywhere), no token-in-localStorage risk. | Auth.js (credentials provider discourages DB sessions); Lucia (deprecated); JWT |
| ADR-004 | Argon2id via `@node-rs/argon2` | OWASP-recommended; prebuilt binaries (works on Windows dev without build tools). | bcrypt |
| ADR-005 | Permission strings + record scopes | Roles are bundles of permissions editable by Super Admin; scopes (`ALL`/`ASSIGNED`/`SELF`/`CHILDREN`) handle teacher/parent/student visibility. | Hard-coded role checks |
| ADR-006 | Service layer is the only mutation path | Single place for authz, validation, transactions, audit; reused by UI actions, REST, imports. | Logic in route handlers |
| ADR-007 | Row-locked counter table for sequences | Gap-tolerant, duplicate-proof under concurrency, format configurable, per-session counters. | Postgres SEQUENCE (no per-year reset/format), `MAX()+1` (races) |
| ADR-008 | Roll-number sort in application with `Intl.Collator` | Deterministic, locale-aware, case/accent-insensitive regardless of DB collation; testable as a pure function. | `ORDER BY name` (collation-dependent) |
| ADR-009 | `Decimal(12,2)` + `decimal.js` | Exact money arithmetic. | Float; integer paise (fine, but Decimal reads clearer in reports) |
| ADR-010 | pgvector in the same Postgres + FTS fallback | No extra vector DB; chatbot still works (keyword retrieval) if no embedding provider is configured. | Pinecone/Qdrant |
| ADR-011 | Chatbot isolated from ERP modules (lint-enforced) | Public endpoint must be structurally unable to read student/staff/salary data. | Prompt-only restrictions |
| ADR-012 | `@react-pdf/renderer` for documents | Pure JS (no headless Chrome in serverless), React templates, good typography. | Puppeteer (heavy, cold starts), pdfkit (imperative) |
| ADR-013 | Razorpay as first payment adapter behind `PaymentGateway` interface | UPI/cards/netbanking in India, signed webhooks. Others pluggable. | Hard-wiring one gateway |
| ADR-014 | Application-level encryption for Aadhaar | Protects against DB dump exposure; HMAC allows duplicate detection without decryption. | Plain column; pgcrypto (key would live in SQL) |
| ADR-015 | shadcn/ui on Radix | Accessible primitives, code owned in repo, Tailwind-native. | MUI (heavier, harder to theme with Tailwind) |
| ADR-016 | **Free-only infrastructure; portable deployment** (2026-11-08) | Owner requirement: zero recurring cost during development. Neon Free for Postgres; `output: "standalone"` Node server so the app runs on any host; every external service optional behind an interface with a no-cost default. Details and limits: docs/FREE_TIER.md. | Vendor-specific runtimes (Vercel-only features, Edge-only code) |
| ADR-017 | Prisma 7 with `@prisma/adapter-pg` (node-postgres) over Neon's **pooled** URL at runtime; **direct** URL for migrations via `prisma.config.ts` | Standard TCP driver works with Neon and any other Postgres, in long-running servers and serverless alike; Neon's pooler handles connection limits. | `@prisma/adapter-neon` (WebSocket, Neon-specific — can be swapped in later for edge/serverless if needed) |
| ADR-018 | **Split file storage**: public media → Cloudinary Free (or local); private documents → private store, **encrypted by the app (AES-256-GCM) before writing** | Public CDN for website images is ideal; confidential files must never be on a public CDN. App-side encryption means any free/cheap S3-compatible provider sees only ciphertext, reducing reliance on provider privacy terms. Downloads only via an authorized route (no public URLs). | Cloudinary private/authenticated assets for documents (still a media CDN, keys shared with public media); unencrypted buckets |
| ADR-019 | Rate limiting and usage metering in **Postgres** | No paid Redis; works across instances. Daily usage caps below free-tier limits (`lib/usage`) stop calls before a provider limit or charge is reached. | Upstash/Redis (extra service) |
| ADR-020 | Chatbot defaults to **no LLM** (FAQ + Postgres full-text search); LLM optional, capped, provider-configurable | Free LLM tiers found so far restrict use by minors or use prompts for training (Gemini). Retrieval-only answers are deterministic, free and cannot hallucinate. Optional local embeddings model for semantic search without an API. | Paid LLM by default |
| ADR-022 | Identity administration via **server actions + pure policy module** (`identity.policy.ts`) | All protection/anti-escalation rules are side-effect-free functions (fully unit-tested offline) called by services inside transactions; UI uses the same functions only to disable options. | Rules embedded in route handlers or UI |
| ADR-023 | shadcn/ui `radix-nova` with project-level overrides (44 px touch sizes, AA-contrast destructive colour, system fonts) | Keeps accessibility and offline builds; components are owned code so overrides are local and reviewable. | Upstream defaults (32 px controls, 4.49:1 error text, Google font fetch at build) |
| ADR-024 | Nonce-based CSP via `src/proxy.ts`; **all pages dynamic** (root layout `dynamic = "force-dynamic"`) | Strict script policy without `unsafe-inline`; static pages can't carry per-request nonces (verified: a prerendered page's scripts were blocked). Also keeps sensitive pages out of shared caches. Cost: no static prerendering — public pages get explicit data caching instead (Roadmap Phase 8). | Hash-based CSP (brittle with framework scripts); no CSP |
| ADR-025 | Super Admin membership changes serialized by a transaction-scoped advisory lock | Correct under READ COMMITTED and transaction-mode pooling; one cheap lock for rare admin operations. | Row locks over joins (unsafe), SERIALIZABLE everywhere (retry complexity) |
| ADR-026 | Layer rules enforced by ESLint + `npm run check:deps` (TypeScript-API cycle/boundary checker) | Boundaries in §3 were conventions only; now CI-checkable without external tools. | madge/dependency-cruiser (external download) |
| ADR-027 | **One app file store** (`lib/storage`: `StorageDriver` local/memory, s3 later) with random keys `<public\|private>/<yyyy>/<mm>/<token>`, per-purpose upload rules (magic-byte type, size, visibility, permission), never-overwrite puts, PRIVATE blobs AES-256-GCM encrypted, every download through `GET /api/v1/files/:id` (404 for forbidden). The school logo is a PUBLIC file in this store (not CMS media); logos are PNG/JPEG only because the PDF engine can't embed WebP/SVG | One authorization and audit path for every file; the DB row (`StoredFile`) is the source of truth, keys reveal nothing; works with no paid service | Public-folder files (no authorization, no audit); signed bucket URLs (need a bucket; harder to revoke); SVG logos (script risk) |
| ADR-028 | **PDF documents** = `lib/pdf` (render + safe response) + `modules/documents` (branding from settings, shared A4 letterhead with fixed header/footer, page numbers, school time zone); rendering happens outside DB transactions | Every future document (ID card, certificate, receipt, report card, slip) shares branding and layout; CPU work never holds a transaction | Per-module ad-hoc templates |
| ADR-030 | **One school per installation — confirmed** (owner decision 2026-11-09; reaffirms ADR-002). Each school runs its own deployment with its **own database (Neon project/branches), private storage, secrets/keys and domain**. No `schoolId`/tenant columns; singleton `SchoolSetting` (`id = 'default'`); globally unique keys (usernames, session names, sequences) are per installation by construction. Code stays school-agnostic: no school facts in code (CMS/settings only), all configuration via env + settings, migrations identical for every installation, so each installation is upgraded independently from the same release | Strongest isolation (a bug can't leak another school's data; one school's outage, quota or restore never touches another); fits per-project free tiers; no tenant filter to forget in every query | Shared multi-tenant database with `schoolId` + RLS (one missed filter leaks data; per-tenant quotas, restores and keys become hard); schema-per-tenant (migration fan-out) |
| ADR-031 | **Dedicated, versioned document-verification key**: verification codes are hashed with `DOCUMENT_VERIFICATION_KEY` (HMAC-SHA256, domain-separated), never `DATA_HMAC_KEY`; each `GeneratedDocument` stores `verificationKeyVersion`. Rotation keeps old keys as `DOCUMENT_VERIFICATION_KEY_V<n>`; verification hashes the typed code under every configured version and accepts a row only under the version it records | Printed codes can't be re-hashed (the raw code is never stored), so rotating a shared key would silently invalidate every issued document; separate keys also limit the blast radius of a leak | Reusing `DATA_HMAC_KEY` (rotation breaks documents); storing codes encrypted (reversible — a leak of DB + key reveals them) |
| ADR-032 | **Guarded, transactional seed.** `npm run db:seed` refuses unless (1) the shell pre-sets no `DOTENV_PATH`/`DOTENV_CONFIG_PATH`/database URL, (2) exactly `<project>/.env` is loaded, (3) `DATABASE_URL`'s endpoint equals the allow-list `SEED_TARGET_ENDPOINT_ID`, is not in `FORBIDDEN_ENDPOINT_IDS` and is not the test endpoint, and (4) the server's own `neon.branch_id`/`neon.endpoint_id` equal `SEED_TARGET_BRANCH_ID`/`SEED_TARGET_ENDPOINT_ID` — in a read-only session first, then again inside the write transaction. All writes run in ONE interactive transaction (timeout 60 s) that starts with `lockSuperAdminGuard`, writes audit rows (`seed.apply`, `user.create`, actor `system:seed`) and verifies the full catalog before commit. A Super Admin is created only if no active Super Admin exists; the seed never elevates or changes an existing account. Logic in `src/lib/db-target-guard.ts` and `prisma/seed-core.ts`; the lock is shared via `src/modules/identity/super-admin-guard.ts` | Seeding is the only non-migration write tool; a wrong `DOTENV_PATH` or edited `.env` must not be able to seed test or production, and an interrupted run must not leave half-granted roles a re-run would skip | Relying on `env:check`/shell discipline only; per-row upserts without a transaction (partial state); creating the Super Admin whenever the username is new (second Super Admin) |
| ADR-033 | **Guarded restore drills.** `npm run backup:drill` reads the SOURCE (development, `.env`) in a **read-only** session and restores into a disposable drill branch (`.env.restore.local`, written by `npm run drill:env`); both live branch/endpoint identities must match allow-lists (`SEED_TARGET_*` for development, `DRILL_TARGET_*` for the drill branch), the target may never be forbidden, development or test, and every table must be empty. No connection strings on the command line. Optional backup file only with `--out`: AES-256-GCM, key from a passphrase via scrypt, header authenticated, `.scbak`, outside the project and the file store, never overwritten. `npm run files:backup` / `files:verify` copy and verify the file store against `stored_file` (read-only, identity-checked; private blobs verified by decrypt + hash). Drill branches are children of development with `--expires-at`; the CLI's `--parent` defaults to production, so drills use explicit parents | A restore rehearsal must be unable to touch production, development or test, and must not put secrets in shell history | Ad-hoc `pg_dump`/`psql` with pasted URLs; restoring into the test branch |
| ADR-034 | **Classes & sections; User as the interim class-teacher reference** (owner decisions 2026-11-10; migration `20261110000000`, applied to **development** 2026-11-10 05:20Z; test pending). `SchoolClass` is session-independent master data (stable unique `code`, case-insensitive unique name via a stored `nameKey`, never deleted — deactivated); Class 11/12 streams are separate classes. `Section` belongs to one academic session and one class, has its own capacity (1–200; new sections default from the class, then `SchoolSetting.defaultSectionCapacity` = 40) and a `version` for optimistic concurrency; section writes hold `FOR SHARE` on the session row so they serialize with session status changes. `Section.classTeacherId → User` (ON DELETE RESTRICT); the service accepts only an active, non-deleted user holding the TEACHER or CLASS_TEACHER role. A **partial unique index** `(academic_session_id, class_teacher_id) WHERE class_teacher_id IS NOT NULL` limits a teacher to one class-teacher section per session; it is declared in `schema.prisma` with Prisma 7's `partialIndexes` **preview feature**, so `migrate diff`/drift checks keep it. Phase 3 reaches the Employee through the existing `User.employeeId`; existing assignments stay valid without data migration (an optional `classTeacherEmployeeId` can be backfilled from it later) | Employee (Phase 3) doesn't exist yet, but teachers already sign in as Users and the ASSIGNED scope is evaluated per user; RESTRICT keeps assignments auditable; a schema-expressed partial index avoids raw-SQL drift (database-migrations skill) | Waiting for Phase 3 to assign class teachers; an FK to a not-yet-existing Employee table; a raw-SQL partial index (later diffs would drop it); a plain composite unique (same NULL semantics, but not the explicit partial index chosen); SET NULL on user delete |
| ADR-035 | **Admissions and students: application-first, approval = registration** (**ACCEPTED** 2026-11-10 — owner approved D1–D12, PHASE_2B_STUDENTS_DESIGN.md §1a; migration `20261111000000`, reviewed, **not applied**). Applicant data lives in `AdmissionApplication` (+ `AdmissionGuardian`) until APPROVED; approval creates the permanent `Student`, `Guardian` links, the session `StudentEnrollment` (capacity checked under the section's row lock) and both IDs (`lib/sequence`) in one transaction. Enrollment → section is a composite FK on (section, session). Roll numbers per section: preview → draft → finalize, then append-only. 10 MB documents go through a dedicated authenticated upload route (KI-048), never server actions. | ADR-036 | **Phase 3A HR model** (owner decisions H1–H14, Q1–Q3, 2026-11-10; PHASE_3_PLAN.md §3a). One school per installation (ADR-030, no `schoolId`). ## 2a. Delivery phases

Module delivery order follows docs/DEVELOPMENT_ROADMAP.md (phases 0–10). The module map below is the target architecture; only `identity` (users, roles, auth, password reset), `settings` (school profile, logo, academic sessions + settings UI — Phase 2a, DB verification pending), `files` (stored-file upload/read/retire), `documents` (branding + letterhead PDF; no domain documents yet), `audit` (writes only — no viewer) and `system/usage` exist today.

UI conventions added 2026-11-08: dates through `lib/format.ts` (school time zone); compact control sizes only for fine pointers (`sm:pointer-fine:`); `app/not-found.tsx` provides the 404 state. **No `loading.tsx` / `<Suspense>` above pages that call `notFound()`** (KI-058, 2026-11-10: a streaming boundary commits HTTP 200 before `notFound()`; `app/erp/loading.tsx` was removed; guarded by `tests/unit/ki058-not-found-status.test.ts`).

## 4. Request lifecycle (mutating)

1. Route handler / server action → `getAuthContext()` (validates session cookie, loads user + permission set, cached per request).
2. `schema.parse(input)` (Zod) → 422 on failure.
3. `service.fn(ctx, input)`:
   - `authorize(ctx, "student.update")` → 403
   - policy check on the target record (scope) → 403/404 (404 when existence itself is sensitive)
   - `prisma.$transaction(async tx => { …mutate…; await audit(tx, …) })`
   - enqueue notifications (after commit)
4. Map result / `AppError` → JSON or redirect.

## 5. Cross-cutting

- **Logging**: structured JSON (pino), request id, no PII (redaction list in `lib/logger`).
- **Rate limiting**: `lib/rate-limit`; Postgres-backed fixed windows (default) or in-memory for single-process dev (ADR-019).
- **Free-tier usage guard**: `lib/usage.consume(metric)` before every metered external call; warns at 80 %, stops at the cap (ADR-019). Applied to login, password reset, enquiry form, chatbot, uploads.
- **Background work**: Phase 1 runs synchronously with idempotent design; bulk PDF/imports use a DB-backed job table processed by a route-triggered worker (cron on hosting). Can move to a queue (e.g. pg-boss) without API changes.
- **Caching**: public pages use Next.js caching with tag revalidation on CMS publish. ERP pages are dynamic, never cached across users.
- **i18n**: UI strings centralised to allow Hindi later (see ROADMAP).

## 6. Hosting topology

**Development (free):** local `next dev` · Neon Free project, `development` branch · private files on local encrypted disk · public media local or Cloudinary Free · email `log` mode · chatbot retrieval-only.

**Production (portable, ADR-016):** Next.js standalone Node server on a host whose terms permit institutional use · Neon `production` branch (or any Postgres 16+ with pgvector) · private S3-compatible bucket with app-side encryption, downloads through an authorized route issuing short-lived signed URLs · Cloudinary for public media · scheduled jobs via host cron hitting `/api/cron/*`. Host choice and its terms are evaluated in docs/FREE_TIER.md and DEPLOYMENT.md (Vercel Hobby is excluded for production: non-commercial personal use only).
